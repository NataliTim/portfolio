Process Transformation for the AI Era

The design system is the source of truth — the foundation that turns AI-assisted design into a deterministic approach.

Design system AI Process Design–development bridge
roleManager of Product Design
scopeDesign process, whole suite
timeframe2025 — present

The component library and design language come first, and every new surface is composed outward from them. That is the approach we have always aimed for — the system leads the work instead of trailing behind it and drifting.

It is now the most critical part of the process. AI works from that foundation, and that is what makes the output deterministic instead of plausible.

A design system is already proven correct. Its components are built, reviewed, accessible and in production — every decision inside it has been made once and validated.

That is why AI has to be built on it. Given a screenshot or a description, an assistant produces a plausible guess that changes every run. Given the tokens, the component repository and the documented patterns, it composes from what is already proven — the same input reaches the same on-system result.

It is the only route from guesswork to a deterministic, predictable outcome.

measured against design system guidelines and standards with styles and patterns

A real component library and design language with documented intent, not a sticker sheet. Without it there is nothing for AI to build from — the system is the precondition, not the output.

Git now carries as much of that foundation as Figma does. We started with Code Connect, moved to MCP, and in some cases work directly against the Git repositories — so the reusable UI components and the design system are read from where they actually live.

MCP is the piece that changes the outcome. Given a screenshot, an assistant guesses. Given the token file, the component repo and the documented patterns, it composes from what already exists — on-system, reusable, buildable.

stage 01 Foundation The Figma library made machine-readable: tokens named, intent documented, coverage audited.
stage 02 System in git Tokens exported as code and the system moved into a GitHub repository — the bridge design and development share.
stage 03 Context layer MCP connected the CLI and Claude Code to the real system; Figma MCP added fast low-fidelity prototyping.
stage 04 Skills and guardrails Agent skills and guardrails written on top of the system, so assistants extend it inside its own rules.

Not a big-bang rollout. Every time a new capability appeared it was evaluated and slotted in as it matured, which kept the system stable while the process around it changed.

Decisions land faster Options are produced inside the system's constraints, so review is about the decision rather than the drawing.
Handoff is ready-to-use HTML Production-grade markup built from real components, not pictures of screens engineering has to rebuild.
Consistency holds under load Many tracks move at once without the system drifting, because every track composes from the same source.

Changing how you work is harder than learning a new tool. I've been doing it for fifteen years — the tools kept changing, the discipline of looking for the better way didn't.

can we do this?Only with a real design system in place — tokens, components, documented patterns, a live repo. The system is the precondition, not the output.
what does it take?The pipeline pieces — tokens as code, a repo, a context layer, assisted build — and a relearning budget for the team.
how do we know it works?Measure the loop: time from idea to consistent, buildable output, and whether it stayed consistent after shipping. Not adoption stats.
where do we start?With the system audit — is it machine-readable, is it in a repo, is intent documented. Then one capability at a time.
