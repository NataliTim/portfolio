One colour system, fourteen UI themes

I modernized the visual foundation of a mature Sales & Service CRM by first understanding how the product was built, then translating a new brand direction into a scalable system across fourteen supported UI themes.

Sales and Service operate inside one CRM ecosystem and rely on the same shared visual foundation: the same navigation, forms, grids, tables, dialogs and interactive states.

Customers use the product every working day and build strong familiarity with its patterns.

Fourteen supported UI themes sit on top of that one foundation, which means a local visual decision can surface across many interfaces and states at once.

The company introduced an updated brand direction while the CRM still relied on an older visual language. New initiatives were already forming, including an AI-assisted service experience and a new sales dashboard.

Before those experiences could be designed consistently, the existing product foundation needed to be updated.

The CRM had evolved over time and was supported by multiple technologies, shared components and deeply established customer behaviours. A visual change could reach navigation, forms, grids, tables, dialogs, interactive and selected states, warnings, primary actions, typography, icons and every reusable component.

How do we modernize the visual foundation of a mature CRM while respecting its technical architecture and the familiarity existing customers depend on?

Before making design decisions, I worked with developers to inventory how the product was actually built: language, framework and version, CSS approach, HTML structure, JavaScript and component libraries, icon libraries and the shared styling architecture.

Design decisions are only scalable when they understand the system that has to implement them.

The system had to become predictable before new experiences could be built on top of it. Seven steps, in the order they had to happen.

semantic roles first

Define what a colour means before deciding what it is

Roles were defined once — application background, surface, navigation, primary action, selection, hover, disabled, warning, error, information, borders and text hierarchy — then mapped consistently across all fourteen supported UI themes.

Typography, icons and reusable components followed the same logic, so one-off styling could be replaced progressively rather than all at once.

Some patterns represented UX debt. Others represented customer familiarity. The work was to tell the two apart.

The objective was not to make the CRM feel like a different product. It was to make the existing product clearer, more consistent and easier to evolve.

The updated interface was visually calmer and more readable. Some long-time customers still reacted negatively to the change.

They were not only reacting to aesthetics. They were reacting to changes in an environment they knew extremely well. A familiar enterprise interface becomes part of how people perform their jobs.

The cost of change is not only implementation. It is relearning.

what changed in my approach
{{ item }}

Later modernization work became more incremental. Instead of treating legacy patterns as something to replace automatically, I became deliberate about separating patterns that create usability problems, patterns that simply look old, and patterns that carry valuable user familiarity.

Modernizing enterprise software is not about making an old interface look new. It is about deciding what should change, what should remain familiar, and creating a system that can evolve without forcing customers to relearn their work.

One foundation, fourteen UI themes, and a clearer way to modernize.
